# Lunar Lockout

A web-based implementation of the Lunar Lockout sliding-block puzzle. Robots slide in cardinal directions until blocked by another robot (wall stops are illegal). Exit robots must reach the center cell (3,3) to win — when they do, they disappear from the board. Helper robots act as blockers only.

Features multiple exit robots (each color-coded), puzzle filtering by difficulty/helpers/exits, blocked cell customization, undo, solution hints with minimum grouped moves, and a self-contained single-file build for easy sharing.

## Hosting & Deployment

### GitHub Pages (recommended)

The repo includes a GitHub Actions workflow (`.github/workflows/deploy.yml`) that builds and deploys automatically on push to `main`.

**One-time setup:**
1. Go to your repo → Settings → Pages → Source → select **GitHub Actions**
2. Push to `main` — the workflow builds and deploys to `https://<user>.github.io/puzzles/`

The workflow runs `npm run build` which copies `public/puzzles.llp` into `dist/`, then deploys the `dist/` directory. The Vite `base` is set to `/puzzles/` to match the GitHub Pages project-site URL.

**Updating puzzles:** commit the new `public/puzzles.llp` and push — the workflow rebuilds and redeploys automatically.

### Other static hosts

Run `npm run build` and deploy the `dist/` directory to any static file server (Netlify, Vercel, S3, etc.). If the site is not served from a `/puzzles/` subpath, update `base` in `vite.config.js` accordingly (e.g., `base: '/'`).

### Offline / single-file sharing

Run `npm run build:bundle` to create `dist/index.bundle.html` — a self-contained HTML file with all JS, CSS, and puzzle data embedded (gzip-compressed). Open directly in any browser with no server needed.

### Puzzle data size

The `public/puzzles.llp` file is committed **without solutions** (positions only) to keep the repo smaller. The app's forward BFS solver computes solutions on demand.

| Variant | Size |
|---------|------|
| Full .llp with solutions | ~15 MB |
| Stripped (no solutions) | ~7 MB |
| Stripped + gzip (transfer size) | ~1.5 MB |
| Bundle HTML (base64-encoded gzip) | ~2.2 MB |

GitHub Pages automatically applies gzip Content-Encoding, so the actual transfer for `puzzles.llp` is ~1.5 MB.

## Generating Puzzles

Puzzles are generated by the C++ enumerator in `ll-solver/`. It uses retrograde BFS to find every solvable board configuration, deduplicates by D4 symmetry and collision signature, and outputs a `.llp` file.

### Building the enumerator

**Linux / g++:**
```bash
cd ../ll-solver
g++ -O3 -std=c++17 -fopenmp -o enumerate enumerate.cpp
```

**macOS / Apple Clang** (requires `brew install libomp`):
```bash
cd ../ll-solver
g++ -O3 -std=c++17 \
    -Xpreprocessor -fopenmp \
    -I$(brew --prefix libomp)/include \
    -L$(brew --prefix libomp)/lib -lomp \
    -o enumerate enumerate.cpp
```

**Without OpenMP** (single-threaded, slower):
```bash
g++ -O3 -std=c++17 -o enumerate enumerate.cpp
```

### Running the enumerator

```bash
./enumerate [max_exits] [max_total] [min_moves] [max_moves]
```

| Argument | Default | Description |
|----------|---------|-------------|
| `max_exits` | 1 | Maximum exit robots |
| `max_total` | 6 | Maximum total robots (exits + helpers) |
| `min_moves` | 1 | Minimum individual slides to solve |
| `max_moves` | 99 | Maximum individual slides to solve |

**Examples:**

```bash
# Standard run: 1 exit, up to 5 helpers, all move counts
./enumerate 1 6 1 99 > ../lunar-lockout/public/puzzles.llp

# Quick test: small puzzle set
./enumerate 1 4 1 10 > test.llp

# Multi-exit: up to 2 exits, 6 total robots
./enumerate 2 6 1 99 > puzzles.llp
```

### Puzzle file format (.llp)

Each line is one puzzle. Full format (with solutions):
```
id|exits|helpers|minMoves|positions|solution
```

Stripped format (committed to `public/`, no solutions):
```
id|exits|helpers|minMoves|positions
```

- **positions**: space-separated `row,col` pairs (exits first, then helpers)
- **solution** (when present): space-separated moves like `AU1` (robot A slides Up, stopped by robot 1)
  - `A`, `B`, `C` = exit robots (by ascending initial position)
  - `1`-`9` = helper robots (by ascending initial position)
  - Direction: `U`=up, `D`=down, `L`=left, `R`=right

The app handles both formats. When solutions are absent, the built-in forward BFS solver computes them on demand.

### Performance notes

| Configuration | BFS states | Memory | Time (4 threads) |
|---------------|-----------|--------|-------------------|
| 1 exit, 5 helpers | 14M | ~200 MB | ~12s |
| 1 exit, 6 helpers | 218M | ~2.5 GB | ~20 min |
| 2 exits, 4 helpers | 17M | ~250 MB | ~15s |

## Game Rules

1. Select a robot by clicking/tapping it
2. Slide it in any cardinal direction using arrow keys, arrow buttons, or swipe
3. The robot slides until it hits another robot (wall stops are illegal — if nothing blocks it, the move is invalid)
4. Exit robots (colored) disappear when they reach the center cell
5. Win by getting all exit robots to the center
6. Consecutive slides by the same robot count as one "move"

## Blocked Cells

Click **Block** in the HUD to enter block mode, then click empty cells to toggle them as blocked (shown with a red hatched pattern). Blocked cells act as walls — robots cannot land on or pass through them, but stopping against one is not a valid move (the "must be stopped by another robot" rule is preserved). The center cell cannot be blocked.

When blocks are active:
- The puzzle list filters out incompatible puzzles, with a count shown in the nav panel
- **Solution** computes a fresh solution respecting the blocks
- **Clear (N)** removes all blocks

Blocks persist across puzzles and browser sessions via localStorage.

The filter uses a three-tier pipeline for efficiency on large libraries (~194K puzzles):

| Tier | Method | Cost |
|------|--------|------|
| Position conflict | Remove puzzles with a robot on a blocked cell | < 1ms |
| Bounding box | Keep puzzles whose bbox doesn't overlap any block | < 2ms |
| Solution trace | Replay stored solution; keep if no path crosses a block | < 50ms |

Puzzles failing the solution trace are conservatively removed without re-solving.

## How It Works

The enumerator uses **retrograde BFS**: starting from all goal states (exits removed, helpers in every valid arrangement), it explores backwards to discover every solvable configuration. Each state gets a depth = minimum slides to solve.

Key optimizations:
- **D4 symmetry**: 8 transforms of the square reduce duplicates by ~8x
- **Collision-signature dedup**: puzzles with identical interaction sequences are merged
- **Packed FlatMap**: 8 bytes per state (key + value in one uint64_t), lock-free parallel insert
- **Three-pass emit**: greedy trace for fast dedup, then DP trace only for survivors to find minimum grouped moves
